# 沟通牌 · 跨端功能规格

> **目的**：定义一台合格的沟通牌客户端**必须 / 推荐 / 可选**实现哪些功能。
> 任何新端（iOS / Desktop / CLI / 第三方）发布前对照本表自查；维护时
> 增改功能在本表登记一行，让"哪些端要跟进、哪些可以延后"一目了然。
>
> 配套：[架构总览](architecture.md) · [游戏规则](game_rules.md) ·
> [客户端实现指南](client_implementation_guide.md) · [多人游戏指南](multiplayer_guide.md)

---

## 0. 三档定义

| 档位 | 含义 | 不实现的后果 |
|------|------|-------------|
| **必须 (MUST)** | 不实现就**不算合格的沟通牌客户端**——影响协议 / 公平性 / 玩家信任 | 不发布；服务端/对手会受影响 |
| **推荐 (SHOULD)** | 不实现端能用，但用户体验明显劣于现有端 | 可发布，但要在 README 标"已知缺失" |
| **可选 (MAY)** | 锦上添花；某些端因平台限制天然没有 | 不影响发布；不需要承诺补齐 |

## 1. 协议层（MUST 全部）

| ID | 功能 | 说明 | 验收 |
|----|------|------|------|
| P1 | `PROTOCOL_VERSION` 握手 | 连接建立后第一帧带版本号；服务端拒绝 mismatch | 用旧版本号连一次主分支 server，应被踢 |
| P2 | 完整 36 字符 sessionId | 不截断，不复用，不 mock；服务端 UUID 必须保留全长 | 抓包看 sessionId 长度 |
| P3 | `Reconnect` 必须在 `onOpen` 内发 | OkHttp / 浏览器 WS / NSURLSessionWebSocket 等异步连接，提前 `send()` 会静默丢弃 | 弱网断线后重连，确认服务端能找回原房间 |
| P4 | 心跳 | 客户端 ≤30s 发一次 `sys.heartbeat`，否则被服务端 idle 60s 后断开 | 后台挂 5 分钟不掉线 |
| P5 | 协议 DTO 与 `:shared/GameMessage.kt` 1:1 对齐 | 字段名、类型、`CardSuit` 枚举字符串大小写都一致 | golden test：发个 `JoinRoom` JSON 与服务端 echo 一致 |
| P6 | 重连后 `applyState` 全量恢复 | 用 `ReconnectSuccess.state` 重建本地状态机；不能依赖增量事件回填 | 断线 30s 后回来，分数 / 手牌 / 桌面与服务端一致 |

> **服务端是单一真相来源**。客户端不要本地推算分数 / 出牌合法性来"补全"
> 服务端的回执；只把服务端推的状态显示出来。

## 2. 游戏功能（MUST 蓝、SHOULD 黄）

### 2.1 单机模式

| ID | 档位 | 功能 |
|----|------|------|
| G1 | MUST | 主菜单可进入单机模式（无需服务端） |

### 2.6 AI 托管 / 速度配置（PROTOCOL_VERSION 3 引入）

| ID | 档位 | 功能 |
|----|------|------|
| G34 | SHOULD | **手动 AI 托管按钮**（双模式）—— 单机：点击后 AI 完全代打你的座位，按钮文本变"取消托管"；多人：发 `player.toggle_ai_takeover { enabled=true }` → 服务端 `isAISubstitute=true`；再点取消 |
| G35 | SHOULD | **暂离 / 回归按钮**（仅多人）—— "暂离" = 立即托管 + 不等 30s 超时（服务端 `isAISubstitute=true` + UI 标记"已暂离"）；"我回来了" = 取消托管 |
| G36 | SHOULD | **单机 AI 出牌速度**（3 档预设：50ms / 400ms 默认 / 1000ms） —— 设置面板 radio；存本地偏好；下一回合生效 |
| G37 | SHOULD | **多人房主：服务端 AI 速度**（3 档预设：100ms / 400ms 默认 / 1000ms）—— 仅房主可见；发 `room.set_ai_speed`；服务端校验 `clientId == hostId` 否则 403；同 PR 房间所有 AI 座位（补位 AI + 玩家托管 AI）即时生效 |
| G38 | SHOULD | **多人玩家：自己的托管 AI 速度**（3 档预设：100ms / 400ms 默认 / 1000ms）—— 每个玩家独立设置；发 `player.set_takeover_speed`；服务端 `playerTakeoverDelayMs[seatIndex]`；该玩家被 AI 接管时用此值 |

> **协议契约（MUST）**：本组特性把 `PROTOCOL_VERSION` 从 2 升到 3。
> 老客户端（v2）连新服务端会被握手层拒（`ERR_PROTOCOL_VERSION_MISMATCH`）；
> 新客户端连老服务端发的 `room.set_ai_speed` / `player.set_takeover_speed` /
> `player.toggle_ai_takeover` 会被忽略（老服无对应 handler）——客户端不应假设
> 这些消息一定生效，UI 应在协议握手后能查询服务端实际的 AI 速度并显示。
>
> **速度档位为什么是 50/100/400/1000**：单机最低 50ms 不影响连接质量；多人最低
> 100ms 是为了避免在网络抖动时 AI 出牌雪崩压垮慢客户端的 UI 渲染；400ms 是
> 综合"看清楚 + 不无聊"的甜点（与 Android 旧默认 1000ms 对比缩短 60%）。

### 2.7 设备分级 · 单机 / 联网 UI 共用 · 玩家数上限

> 与架构约束 6/7/8 对齐（参见 [`architecture.md`](architecture.md) §五 与
> [`CLAUDE.md`](../CLAUDE.md) §二）。本节是**强制规格**，不是建议。

| ID | 档位 | 功能 |
|----|------|------|
| U1 | MUST | **单机 / 联网同一套游戏屏幕**：每个端的单机 AI 模式与多人联网模式复用同一渲染层；单机引擎把本地状态映射为与服务端推送同构的 `SerializedGameState` 后再交给 UI |
| U2 | MUST | **Android 优化版作为布局基线**：新端 / 新 form factor 默认以 Android 版的信息架构（手牌位 / 头像排布 / 中央出牌 / 操作按钮 / 字号层级）作为起点，按屏幕尺寸适配 |
| U3 | MUST | **小屏（Compact, < 600 dp）禁用 8 / 10 / 12 人模式**：CreateRoom UI 隐藏或 disable 这些选项，并提示"该模式需要平板及以上屏幕" |
| U4 | MUST | **平板 / 三折手机展开态（Medium, 600–1200 dp）支持 6 / 8 人** |
| U5 | MUST | **桌面 / Web 大窗（Expanded, ≥ 1200 dp）支持 6 / 8 / 10 / 12 人** |
| U6 | MUST | 服务端**拒绝**任何 `expectedPlayerCount > 6` 但客户端声明 `screenClass = Compact` 的 CreateRoom 请求（防止前端绕过；返回 `ERR_PLAYER_COUNT_REQUIRES_LARGER_SCREEN`） |
| U7 | SHOULD | **牌副数随玩家数变化**：6 人 = 4/6 副；8 人 = 6/8 副；10 人 = 8/10 副；12 人 = 8/10/12 副。当前 `:shared/Deck.kt` 仅支持 4 副，扩展需把 `Deck.reset()` 参数化（接 `deckCount: Int`）+ 补 `commonTest` 才能在 UI 暴露；服务端 MUST 校验组合合法 |
| U8 | SHOULD | 设备旋转 / 窗口 resize 实时切换 LayoutMode；进行中的对局**保持当前模式**直到本局结束（避免中途位移导致点错牌） |

#### 设备分级对照表（速查）

**(a) 终端 → 玩家数**

| 终端类型 | 屏幕宽度（dp）| LayoutMode | 允许玩家数 |
|---------|--------------|-----------|-----------|
| 手机普通竖屏 / 折叠机折叠态 | < 600 | Compact | **仅 6 人** |
| 平板 / 三折手机展开态 / 手机横屏 | 600–1200 | Medium | 6 / 8 人 |
| 桌面 / Web 大窗 / 大屏笔记本 | ≥ 1200 | Expanded | 6 / 8 / 10 / 12 人 |

**(b) 玩家数 → 牌副数**（独立于终端，按"每人 ~36 张下限、~54 张上限"规划）

| 玩家数 | 允许牌副数 | 总张数 | 每人手牌张数（取 max 副数）|
|-------:|-----------|-------:|--------------------------:|
| 6 人 | 4 / 6 副 | 216 / 324 | 36 / 54 |
| 8 人 | 6 / 8 副 | 324 / 432 | 40 / 54 |
| 10 人 | 8 / 10 副 | 432 / 540 | 43 / 54 |
| 12 人 | 8 / 10 / 12 副 | 432 / 540 / 648 | 36 / 45 / 54 |

> 副数下限保证每人至少 ~36 张手牌；上限固定为"每人一副"（54 张）让分值牌
> （K/10/5）能合理散到所有玩家。服务端 MUST 校验 `(playerCount, deckCount)`
> 组合合法，否则拒绝 CreateRoom。

> **教训**：UI 双份（单机一套 + 联网一套）必然漂移。把两条数据路径合到同一个
> 渲染入口能把 UI 回归面减半；以 Android 优化版作为基线则避免新端反复试错。
> 小屏强制 6 人是因为 8+ 个玩家头像在 < 600 dp 排不开（详见 `LayoutMode.kt`
> 注释中"5-6 个玩家头像至少要 600 dp 才能横排"）。

## 4. 移植清单（新客户端发布前自查）

> 复制本节到新客户端的发布 PR 描述，逐项打勾。

### 4.1 协议
- [ ] 实现 P1–P6 全部 6 项
- [ ] 与 `:shared/GameMessage.kt` 跑过一次 round-trip 测试（发 JSON 给 server，收回的 Pong 字段一致）
- [ ] `PROTOCOL_VERSION` 跟主分支一致

### 4.2 必须功能
- [ ] G1, G2, G3（单机）
- [ ] G5, G6, G7, G8, G9, G11, G12（多人核心）
- [ ] G16–G22（游戏内 UI 必备）
- [ ] G28, G29（结算）
- [ ] U1（单机 / 联网共用同一渲染层）
- [ ] U2（以 Android 优化版作布局基线）
- [ ] U3, U4, U5（按 LayoutMode 限制玩家数；小屏仅 6 人）
- [ ] U6（服务端拒绝小屏的 8+ 人 CreateRoom）

### 4.3 推荐功能（缺哪些要在 README 列出）
- [ ] G4（单机存档）
- [ ] G10（房主管理）
- [ ] G13（断线重连）
- [ ] G23（提示按钮）—— 客户端是否调 `:shared/CardRules`
- [ ] G24（选中视觉反馈）
- [ ] N4（离线提示）
- [ ] N5（错误码文案）

### 4.4 安全 / 公平性自检
- [ ] 客户端**不本地修改**手牌 / 已收 / 队伍分；只展示服务端数据
- [ ] 客户端**不绕过** `:shared/CardRules.canBeat` 直接发 `PlayCards`（会被服务端拒，但仍是规范违例）
- [ ] 客户端**不持久化** `sessionToken` 跨设备 / 跨应用安装
- [ ] 用户信息 / 昵称只发到本服务端，不上报第三方

### 4.5 性能
- [ ] 心跳间隔实测 ≤ 30s
- [ ] 重连指数退避正确（2/4/8/16/32s 上限 5 次）
- [ ] UI 不卡帧 < 60fps（移动端） / < 120fps（PC）

### 4.6 测试矩阵（最低）
- [ ] 单机：完整玩完 1 局，分数与 `:shared/SettlementCalculator` 一致
- [ ] 多人：本地起 server，2 个真人 + 4 AI 玩到结算
- [ ] 重连：断网 30s 回来，状态恢复 OK
- [ ] 与 Android / Web 客户端混合开局：4 个 Android + 1 新端 + 1 AI 可正常进行

## 6. 变更流程

修改本文必须连带：

1. 在第 5 节"现状对照表"加 / 改对应行
2. 若改动协议层（第 1 节）——同 PR 改 `PROTOCOL_VERSION`，触发 `protocol-syncer`
3. 若降级某项 MUST → SHOULD（极少见）—— 在 PR 描述写理由 + 影响面分析
4. 4-gate（CI / Codex / Claude /review-pr / 真机）按 [PR 模板](../.github/pull_request_template.md) 走
